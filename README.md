# MDA-MDH Integration

A working bridge between two independent model-driven CUDA code generators, demonstrated end to end on a 2D Poisson equation solver.

## Overview

This repository shows that a UML model from an existing MDA (Model-Driven Architecture) toolchain can drive MDH (Multi-dimensional Homomorphisms), a separate, performance-oriented CUDA code generator, instead of MDA's own naive code generator.

Both systems are real, pre-existing projects that independently generate CUDA kernels for the same computation: a 5-point Jacobi stencil solving the 2D Poisson equation. This repository adds a small bridge component that reads the UML model MDA already uses and produces an MDH specification from it. That specification is then compiled through MDH's own generator to produce a tiled, tuned CUDA kernel, and the result is benchmarked against three things: MDA's own naive kernel, MDH's own hand-written kernel (with no UML or bridge involved at all), and a serial CPU baseline. The second comparison matters because it rules out the obvious objection "wouldn't MDH alone just be better than the two bridged together?" - see `RESULTS.md` for the measured answer.

## Background

| Term | Meaning |
|---|---|
| MDA | Model-Driven Architecture. A UML activity diagram is transformed into CUDA source using ATL (ATLAS Transformation Language) for the model-to-model step and Acceleo for the model-to-text step. |
| MDH | Multi-dimensional Homomorphisms. A C++ specification (buffers tagged by dimension role, a per-element function, a reduction function) is compiled through a generator that produces a tiled, parameterized CUDA kernel. |
| Bridge | The new component added in this repository. Reads the UML model directly and emits an MDH specification from it. |
| Serial baseline | A single-threaded CPU implementation of the same algorithm, used to measure real speedup for every kernel tested. |

## What is in this repository

One worked example - the 2D Poisson equation, solved with a 5-point Jacobi stencil - carried through four independent, directly comparable code paths:

1. **MDA's own naive GPU kernel.** Already generated by the existing Eclipse/ATL/Acceleo toolchain, copied in unmodified.
2. **MDH's own hand-written GPU kernel.** The original MDH specification, with no UML model or bridge involved anywhere - included specifically to check whether the integration costs any performance.
3. **MDH's tuned GPU kernel, generated from the UML model.** Produced by the new bridge script, then compiled through MDH's existing generator.
4. **A serial CPU reference implementation.** The baseline every speedup number in this repository is measured against.

All four are run through the same test harness, at the same grid sizes, with the same convergence criterion, so the resulting numbers are directly comparable. See `RESULTS.md` for the full measured table.

## How the bridge works

`bridge/uml_to_mdh_bridge.py` parses the UML model (`mda_reference/poisson_dsc.uml`) as XML and looks for the exact node pattern that MDA's own ATL transform (`poisson_uml2cuda.atl`) already recognizes. If every expected node is present with the expected type, it maps each one to the matching MDH construct:

| UML node recognized | MDH construct produced |
|---|---|
| `SelectNode` | Parallel index dimensions `L(1)`, `L(2)` |
| `ReadNeighbours` (top / bottom / left / right) | 5-point stencil neighborhood on an `input_stencil_buffer` |
| `ApplyStencil` | The per-element scalar function `f` |
| `StoreValue`, with no reduction loop present | `result_buffer`, `md_hom<2, 0>` |

If the pattern does not match exactly, the bridge aborts with a clear error instead of guessing.

**This is a hand-written, pattern-specific translator, not a general UML-to-MDH compiler.** A different kernel shape - a different stencil, a different reduction, renamed nodes - needs a new recognizer added to `uml_to_mdh_bridge.py`, in the same way it would need a new rule added to MDA's own ATL transform. This scope limitation is intentional and is restated in `RESULTS.md`.

See `diagrams/pipeline.puml` for the full component diagram (what the pieces are and how they depend on each other) and activity diagram (the bridge's step-by-step logic), written as real UML in PlantUML's text syntax.

## Repository layout

| Path | Contents |
|---|---|
| `mda_reference/` | Copies of the UML model, the ATL transform, and MDA's own naive-kernel output. Reference material, not executed here except where noted. |
| `mdh_framework/` | Copy of the MDH generator core (`md_hom_generator.hpp`, headers, sources). |

## Results summary

**Measured compute time:**

| Grid | Serial CPU | MDA alone | MDH alone | Integrated |
|---|---|---|---|---|
| 64x64 | ~0.11 s | 0.038 s | 0.028 s | 0.028 s |
| 128x128 | ~1.76 s | 0.156 s | 0.150 s | 0.156 s |
| 256x256 | ~28.7 s | 1.476 s | 1.239 s | 1.245 s |

**Integrated compared directly:**

| Grid | Integrated vs. MDA alone | Integrated vs. MDH alone |
|---|---|---|
| 64x64 | 1.36x faster | 1.00x (tied) |
| 128x128 | 1.00x (tied) | 0.96x (tied - noise) |
| 256x256 | 1.19x faster | 1.00x (tied - noise) |

**Verdict:** Integrated beats MDA alone at 64x64 and 256x256, ties it at 128x128, and never loses to it anywhere. Integrated is tied with MDH alone at every size - expected, since the two are compiled from byte-for-byte identical CUDA source (see `RESULTS.md`, "Verification"). That tie is a feature: it means the bridge costs nothing.

Full tables, repeated-trial data, and discussion in `RESULTS.md`.

## Reproducing the results

```bash
cd "~/Integration of MDA and MDH"

# 1. Bridge: UML model -> MDH specification -> tuned kernel
python3 bridge/uml_to_mdh_bridge.py
mkdir -p build && cd build && cmake .. && make && cd ..
(cd generated && ../build/poisson_from_uml)   # -> poisson_1.cu, poisson_2.cu

# 2. Integrated (UML -> MDH) GPU vs. serial, at each grid size
for NX in 64 128 256; do
  NI=$((NX-2)); NWG=$((NX/16))
  nvcc bench/test_poisson_converge.cu generated/poisson_1.cu \
    -o generated/test_poisson_converge_${NX} -DNX_GRID=${NX} \
    -DTYPE_T=double -DTYPE_TS=double -DCACHE_L_CB=0 -DCACHE_P_CB=0 \
    -DG_CB_RES_DEST_LEVEL=2 -DG_CB_SIZE_L_1=${NI} -DG_CB_SIZE_L_2=${NI} \
    -DL_CB_RES_DEST_LEVEL=1 -DL_CB_SIZE_L_1=16 -DL_CB_SIZE_L_2=16 \
    -DP_CB_RES_DEST_LEVEL=0 -DP_CB_SIZE_L_1=1 -DP_CB_SIZE_L_2=1 \
    -DNUM_WG_L_1=${NWG} -DNUM_WG_L_2=${NWG} -DNUM_WI_L_1=16 -DNUM_WI_L_2=16 \
    -DOCL_DIM_L_1=1 -DOCL_DIM_L_2=0
  ./generated/test_poisson_converge_${NX}
done

# 3. MDA alone (naive GPU) vs. serial, at the same grid sizes
for NX in 64 128 256; do
  nvcc bench/test_poisson_mda.cu bench/mda_kernel.cu \
    -o generated/test_poisson_mda_${NX} -DNX_GRID=${NX} -DN=${NX}
  ./generated/test_poisson_mda_${NX}
done

# 4. MDH alone (hand-written spec) vs. serial, at the same grid sizes
mkdir -p generated/handwritten
(cd generated/handwritten && ../../build/poisson_handwritten)
for NX in 64 128 256; do
  NI=$((NX-2)); NWG=$((NX/16))
  nvcc bench/test_poisson_converge.cu generated/handwritten/poisson_1.cu \
    -o generated/test_poisson_handwritten_${NX} -DNX_GRID=${NX} \
    -DTYPE_T=double -DTYPE_TS=double -DCACHE_L_CB=0 -DCACHE_P_CB=0 \
    -DG_CB_RES_DEST_LEVEL=2 -DG_CB_SIZE_L_1=${NI} -DG_CB_SIZE_L_2=${NI} \
    -DL_CB_RES_DEST_LEVEL=1 -DL_CB_SIZE_L_1=16 -DL_CB_SIZE_L_2=16 \
    -DP_CB_RES_DEST_LEVEL=0 -DP_CB_SIZE_L_1=1 -DP_CB_SIZE_L_2=1 \
    -DNUM_WG_L_1=${NWG} -DNUM_WG_L_2=${NWG} -DNUM_WI_L_1=16 -DNUM_WI_L_2=16 \
    -DOCL_DIM_L_1=1 -DOCL_DIM_L_2=0
  ./generated/test_poisson_handwritten_${NX}
done
```

Requirements: GCC/G++ with C++14, CMake 2.8.11 or newer, CUDA toolkit with `nvcc`, an NVIDIA GPU, Python 3.

## Scope and limitations

- The bridge recognizes exactly one UML node pattern (the one described above). It is not a general-purpose UML-to-MDH compiler.
- Only the Poisson example is covered. Extending this to other kernels (for example matrix multiplication) means adding a new recognizer to the bridge and a new MDH specification template.
- Nothing outside this repository's own folder is modified by any script here. `mda_reference/`, `mdh_framework/`, and the original contents of `bench/` are copies of files from separate, pre-existing projects; those original projects are untouched.
